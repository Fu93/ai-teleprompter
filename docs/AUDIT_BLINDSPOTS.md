# 稽核盲區盤點:排除條件會不會讓缺陷漏過(2026-10-05)

## 這份文件存在的原因

這個專案的稽核體系很成熟(6 支稽核腳本、狀態基線、豁免上限、負向驗證慣例)。
但它有一個**結構性的弱點**:每一條規則都有「為了不誤報而設的排除條件」,
而排除條件是規則裡唯一**不會被驗證**的部分 —— 測試驗證的是「該報的會報」,
沒有人驗證「被排除的那些是不是真的都沒問題」。

2026-10-05 這一輪把 `domAudit` 的每條規則都反問了一次「它會讓什麼漏過」,
找到兩個真實盲區。兩者的成因相同:**排除條件本身是對的,但它假設了一個
不總成立的條件**,而那個假設從來沒有被檢查過。

同日追加的**第三類**盲區不在規則裡,而在量測端:稽核腳本自己以為的
「清空」其實是「解除覆寫」。它的危險性更高 —— 規則量錯會漏報缺陷(少一個問題),
量測端量錯會**憑空造出一個問題**,而且那個問題看起來完全合理。詳見下方盲區 3。

這份文件是**可重複的**:下面每一條排除條件都附上「它可能讓什麼漏過」,
下次新增規則時照著填一遍,就是一份同樣的盤點。

---

## 已確認的四個盲區(本輪已修)

第四個(盲區 4)是同日追加的:它不是某一條規則的排除條件錯了,而是**所有頁面
稽核的共同前提**錯了 —— 它們量的是「頁面畫了什麼」,而使用者看到的是「視窗層
合成之後的結果」。

### 盲區 1:`thin-slider` 量錯對象 —— 一條**從未觸發過**的規則

| 項目 | 內容 |
|---|---|
| 規則 | `thin-slider`:range 軌道高度 < 8px(滑鼠難以瞄準) |
| 原本宣稱要量 | `::-webkit-slider-runnable-track` 的高度 |
| 實際量到的 | **元素**的 `getBoundingClientRect().height` |

原本的實作是 `isRange ? r.height < 8 : ...`。而 `r.height` 是元素的
boundingRect —— 也就是**命中帶**,不是軌道。

兩件事讓它永遠沉默:

1. range 的元素高度是命中帶,第四輪 P2-2 把它從 22px 改成 **28px**。
   從那之後 `28 < 8` 永遠不成立。
2. 軌道是**偽元素**,`getBoundingClientRect()` 根本量不到它 ——
   就算元素高度很小,量到的也不是軌道。

**證據(不是推論)**:在真實 Chromium 上量過 —— 軌道 2px 的 range,
元素高度仍是 28px,舊規則的判定結果是「不報」。而且 `docs/audit` 底下每一份
`report.json` 裡**都沒有出現過 `thin-slider`**,證明它一次都沒抓到過東西。

這是最危險的一種失效:**規則看起來在工作**(它有名字、有註解、有門檻),
但永遠不會響。沒有規則比壞規則誠實。

**修法**:量軌道,並**重新校準門檻**。這一點是關鍵 ——
照原文的 8px 會讓六個滑桿全部誤報(真實軌道是 4px,而且那是被 P2-2 刻意
保留的正確視覺)。所以門檻降到 **3px**:報的是真的細到看不見的軌道。
**先量過才定門檻**,而不是沿用文件裡的數字。

新增 `isThinTrack()`,並讓 `isSmallTarget()` 對 range 一律回 false
(拆成兩條規則,避免同一個缺陷被報兩次 —— 報告的問題數是稽核閘門的基準)。

#### ⚠️ 修這個時踩到的第二個坑:`getComputedStyle` 量不到軌道

**第一次修正同樣是壞的**,而且差點就這樣交付了。寫完之後我在真實瀏覽器上
複驗,發現:

```js
getComputedStyle(el, '::-webkit-slider-runnable-track').height
// 軌道設 2px → "28px"    ← 元素的高度
// 軌道設 4px → "28px"
// 軌道設 6px → "28px"
```

不管軌道設成多少,它**永遠回傳元素高度**,而且**不報錯、不警告**。
帶引號的寫法(`"'::-…'"`)與 `getPropertyValue('height')`)也一樣是 28px。

**這意味著我原本的修正只是「把一條不會觸發的規則換成另一條不會觸發的規則」。**
唯一救回來的原因是:我在寫完之後又跑了一次真實瀏覽器複驗,而不是看到測試
變綠就收工。

可行的方法是走 **CSSOM**:`document.styleSheets` → `cssRules` → 找綁到這個
元素的 `::-webkit-slider-runnable-track` 規則,讀它的 `style.height`。
同一組實測下 CSSOM 正確回傳 2 / 4 / 6。已用它實作。

**更值得記錄的是測試層的教訓**:第一版測試 stub 了 `getComputedStyle`,
讓它在收到偽元素選擇器時回傳軌道高度 —— **測試全綠**。但它驗證的是
「我以為的行為」而不是「實際行為」,等於**在測一個假世界**。改 stub
`document.styleSheets` 之後,測試才真的在驗規則讀的那條路徑。

邊界(cssRules 拋出就跳過、不解析萬用選擇器、讀不到就不報)寫在
`trackHeightFromCssom` 的註解裡。

### 盲區 2:規則 5 把「在 label 裡」當成「有名稱」

| 項目 | 內容 |
|---|---|
| 規則 | `no-accessible-name`:可操作控制項沒有無障礙名稱 |
| 排除條件 | `&& !inLabel` —— 在 `<label>` 裡的控制項一律略過 |
| 假設 | label 會提供無障礙名稱 |

假設只在 label **有文字或 title** 時成立。實測過的反例:

```html
<label><input type="checkbox"></label>
```

`label.textContent` 是空字串、沒有 `aria-label`、input 也沒有 ——
螢幕閱讀器拿到的是**空名稱**,而規則因為「它在 label 裡」而略過。
與盲區 1 的 `small-label-target` 是同一族問題:**為了不誤報而做的排除,
自己變成了一個看不見缺陷的地方。**

**修法**:改成「只有在 label **真的提供得到名字**時才略過」
(`nameFromLabel.length > 0`)。有文字、有 title 的 label 照樣略過(不誤報)。

### 盲區 3:稽核腳本把「解除覆寫」當成「清空」—— 量測端自己量錯

前兩個盲區在**規則**裡,這個在**量測端**,而且它的症狀是反方向的:
不是漏報缺陷,而是**憑空多出一個問題**。

- **事實**:`audit:states` 長期回報 `hotkey-conflict-stale`
  (「衝突清單清空後畫面上還留著警示」)。追查後確認:警示沒有留著,
  是**清除的那一步根本沒清**。
- **根因**:`currentHotkeyConflicts()` 回傳 `forced ?? conflicts`。所以
  `__auditForce('app.hotkeyConflicts', null)` 的語意是「解除覆寫、回到真實名單」,
  而不是「清空」。這台機器上 `Alt+K` 等熱鍵真的被別的程式佔走,
  於是解除之後警示如實長回來 —— 量測端把自己的錯記成了產品的缺陷。
- **為什麼長久沒被抓到**:`null` 與 `[]` 在**乾淨機器上看起來一模一樣**
  (真實名單本來就是空的)。這個錯只在有真實衝突的機器上現形,
  而 CI 通常沒有衝突。與盲區 1 同一個病根:**通過測試只證明量得一致,
  不證明量的是對的那個世界。**
- **修法**:抽出 `scripts/lib/hotkey-override.mjs` 的 `clearHotkeyOverride()`,
  把「`[]` 清空 → 量測 → `null` 解除」三步寫成可測的函式;
  測試**驅動產品自己的 store**並預先設好真實衝突(`['Alt+K']`),
  而不是拿一個假 store 去驗。解除失敗會報 `unreached`,不會讓後續狀態
  繼續在一個「假裝沒有衝突」的世界裡被量。
- **可複用的教訓**:任何「強制覆寫某個狀態」的稽核橋,**清除語意必須是
  明確的值,不能是 `null`** —— `null` 在這個專案裡已經有兩種意思
  (`preflight.models` 與 `app.hotkeyConflicts` 都不一樣)。
  要覆寫的狀態,值域裡請留一個明確的空值。

### 盲區 4:視窗層 —— 所有頁面稽核的共同盲區(2026-10-05 追加)

| 項目 | 內容 |
|---|---|
| 現象(使用者) | 浮層「四個角有白邊,應該是弧線卻變成方正的」 |
| 頁面層的答案 | 角是精確的弧(corner-scan / audit:edge 的角落斷言全綠) |
| 真正的位置 | **視窗層**:底色(`backgroundColor` 預設 #FFF)與 `setBackgroundMaterial('acrylic')` |

所有稽核腳本(ui / edge / deep / glass-edge / states / effects)的共同前提是
「Playwright 對 **page** 截圖」。而 `transparent: true` 的視窗有一層頁面之外的
合成:webContents 底色、DWM 材質、視窗邊框。那一層拍不到 —— 於是「頁面量起來
是對的」與「使用者看到的是對的」之間,有一道沒有人看守的縫。

這道縫不是沒被發現,而是**被量錯的方法錯誤地關上了**:
`scripts/attic/probe-desktop.mjs` 就是為它寫的,但它有兩個讓它整支失效的錯:

1. **座標系混用**:它拿 `window.screenX/screenY`(CSS px)去量 `CopyFromScreen`
   的桌面點陣圖(裝置 px)。本機是 200% DPI → 它量的矩形只有實際視窗的一半大、
   位置也偏一半,**量到的是桌布對桌布**,所以四個角永遠「透明」。
2. **判定寫反**:`pageVisible` 用 `channels[3].mean < 250` 當「有內容」——
   全透明頁面的 alpha 平均是 0,於是「全透明」被判成「有內容」。

兩個錯的方向相反:第一個讓它看不到缺陷,第二個**憑空造出一個缺陷**
(「沒有去背」)。而那個結論還被當成限知邊界記進了 CHANGELOG。

#### 這次怎麼量對的(方法本身值得留著)

- **座標系**:`screenX × devicePixelRatio` 才是桌面點陣圖的座標。先讀 dpr,
  並把「視窗矩形有沒有完整落在擷取範圍內」印出來 —— 本機的擷取只有虛擬螢幕的
  前 900 裝置 px 高,展開面板的底部其實被切掉了。
- **對照組是關鍵**:材質有沒有在畫,不需要跟桌布比。**只切換 `overlay.glass`
  這一個設定**(頁面其餘完全相同)再逐像素差分 —— 桌面內容在兩張之間不變,
  差值就只可能來自那一個開關。藥丸(材質本來就是 auto)是天然控制組:它必須是
  0,否則代表差分本身有雜訊。實測藥丸 0、展開 95.4%(平均 165 級、角落 211
  vs 桌布 22)—— 缺陷與修正都靠這一組對照才站得住。
- **不可以用 `''` 還原行內樣式**:浮層的透明是 `OverlayApp` 掛在
  `documentElement/body` 上的**行內** `background: transparent`。探測腳本若用
  `style.background = ''` 收尾,會清掉行內值、露出樣式表裡的深色 body ——
  於是**下一次量測拍到的是自己剛剛造出來的方角矩形**。(這一輪真的踩到:
  展開形態的第一次量測就是這個假象,差點當成根因交付。)
- **頁面「全透明」要用藏 UI,不是改背景**:`#root { visibility: hidden }`
  保留 App 自己的行內透明設定,量到的才是「視窗層自己畫了什麼」。
- **差分之外還需要「絕對值對照組」**:差分能抓到「這一層在畫」,但若兩張都錯
  得一樣(例如兩張都是白底),差分是 0。真正的真值是**把視窗搬走、量同一塊桌面**
  (`A1` vs `C`)——最後一層就是這樣才看出來的。

#### 結果:同源的兩層,差一點只修到一層

1. **系統材質**:展開形態下铺滿視窗矩形(切換它會改變矩形 95.4% 的像素、
   平均 165 級;角落 211 vs 桌面 22)。藥丸(材質本來就是 auto)是對照組:0。
2. **視窗底色**:`BrowserWindow` 的 `backgroundColor` 預設是 **#FFF** —— 面板的四個
   圓角外露出的是白底(246,245,244,…),而同一塊桌面沒有視窗時是 43,43,43,…。
   這一層跟 acrylic 無關,**藥丸也有**(240 vs 桌面 40),而且它才是使用者最先
   看到的那個「白邊」。

量測過程中的三個反直覺事實(每一條都改寫了修法):

- **選項不生效**:`new BrowserWindow({ transparent: true, backgroundColor: '#00000000' })`
  建立後 `getBackgroundColor()` 仍回 `#FFFFFF`,四個角照樣是白補丁 —— 要在視窗
  存在**之後再呼一次 `setBackgroundColor('#00000000')`** 才真的變透明(240 → 38≈桌面 40)。
- **兩層會互相覆寫**:`setBackgroundMaterial('none')` 會把底色**重設回白色**
  (順序實測:底色透明 → 37=桌面;再呼叫材質 → 232=白)。所以「先設透明底色、
  再設材質」等於白設 —— 而那個材質呼叫原本就在**每一幀**的尺寸同步路徑上。
  最後的修法是**完全不碰材質**(不是「把它設成 none」)。
- **修好一層不等於修好了**:拿掉材質之後,玻璃切換的差分確實是 **0 像素改變**
  —— 但那個量測只證明「這一層沒在畫」,對「另一層還在畫白底」完全無感。
  差分的極限就在這裡:它只能證明「與對照組不同」,對「兩張都一樣錯」是盲的。

## 每條排除條件盤點(可重複填寫)

| 規則 | 排除條件 | 它可能讓什麼漏過 | 狀態 |
|---|---|---|---|
| `small-tap-target` | label 內的輸入框略過 | label 自己太小 → **已由 `small-label-target` 接手(本輪新增)** | 已補 |
| `small-tap-target` | range 改看軌道 | 元素/軌道量錯對象 → **本輪修好並重新校準門檻** | 已補 |
| `no-accessible-name` | label 內的控制項略過 | 空 label 的控制項其實無名 → **本輪修好(改為條件式略過)** | 已補 |
| `no-accessible-name` | `type` 為 hidden/submit/button/reset/image | value 為空時 submit 按鈕可能被誤判為有名字 | **待確認**(實務上 Button 的隱含名稱來自 value,空 value 是真的沒名稱) |
| `low-contrast` | 前景色 alpha ≤ 0.5 的文字不報 | 半透明文字對比不足 → 但 alpha 低本身就是可讀性問題,`tiny-text` 或許更合適 | 刻意(避免把半透明當成對比問題) |
| `truncated-no-label` | 自身橫向可捲動的元素略過 | 捲動容器裡被截斷的文字沒有 title → 容器可捲,使用者捲得到 | 刻意 |
| `h-overflow-container` | 有 `data-allow-h-scroll` 宣告的元素略過 | 宣告被濫用就會漏過。**目前全 repo 只有 1 處使用** | 已確認範圍可控 |
| `clipped` | 容器在該軸可捲動時不算裁切 | 使用者捲得到就不算問題 | 刻意 |
| `tiny-text` | 只看「本身有文字」的元素 | 偽元素(`::before`/`::after`)產生的文字完全沒被量到 | **已確認為盲區,但暫不修**(見下) |
| 所有規則 | `r.width === 0 \|\| r.height === 0` 就跳過 | 隱藏但之後會顯示的元素(如收合的面板)量不到 | 刻意(靜態量測的固有限制) |
| 所有規則 | `MAX_SCAN_ELEMENTS = 3000`(除錯層) | 超過 3000 個元素的頁面(長會議逐字稿)不再掃描 | 刻意(除錯層不能拖慢 App) |

### 為什麼 `::before`/`::after` 的文字暫不修

它是真的盲區(pseudo-element 的 `content` 不在 `querySelectorAll('*')` 裡),
但**量不到它的樣式**:這個專案目前沒有讀 pseudo-element 計算樣式的程式碼,
而它的成本與風險(偽元素的 content 可能是 icon、可能是裝飾)不相稱。
與其加一條會誤報的規則,不如記在這裡,等真的出現案例再處理。

## 怎麼重複這份盤點

新增一條規則時,照著問這六個問題(前三個看規則,後三個看量測端):

1. **這個排除條件假設了什麼?** 假設成立嗎?誰能讓它不成立?
   (盲區 2 就是「假設 label 有文字」,而沒有人檢查 label 到底有沒有文字。)
2. **被排除的東西,由誰負責檢查?** 若答案是「沒有別人」,那這個排除
   就是一個看不見缺陷的地方,必須補一條規則接手。
3. **這條規則在真實環境下**「真的會響嗎」?——
   這是盲區 1 專屬的問題。寫完之後在真實瀏覽器裡量一次:
   一條從未觸發過的規則,和沒有規則在效果上是一樣的,但看起來更可靠。

`getComputedStyle(el, '::-webkit-slider-runnable-track')` 在真實 Chromium 上
**回傳元素高度而不是軌道高度**,而且不報錯。要讀軌道必須走 CSSOM
(`document.styleSheets` → `cssRules`),這在 node 測試環境也不可用
(vitest 是 `environment: 'node'`)。**涉及偽元素的規則,門檻要用真實瀏覽器
量過的值,再用 stub 的 CSSOM 在單元測試裡釘住判斷邏輯** ——
而且 stub 的必須是**規則實際讀的那個 API**,否則測試驗證的是幻覺。

### 最重要的一條:綠燈不等於正確

這個專案的每一條規則都有測試、都有負向驗證的慣例。而盲區 1 說明:
**負向驗證只能證明「拿掉修正會紅」,不能證明「修正後量到的是對的東西」。**

盲區 1 的前兩版都通過了完整測試與負向驗證 —— 第一版因為「拿到的高度小於
門檻」而紅(修好後不紅了),但它量的東西本身就是錯的。

所以新增第 4 個問題:

4. **這個量測方法,在真實瀏覽器裡真的回傳你要的東西嗎?**
   對偽元素、CSSOM、Canvas、Web Audio 這類「需要特定引擎才拿得到」的東西,
   這個問題不能靠單元測試回答。寫完之後在真實頁面上跑一次,並且
   **把量到的原始值寫進規則的註解** —— 讓下一個人不必重做這個實驗。
5. **這個「強制狀態」的控制項,清除語意是什麼?**(盲區 3 專屬)
   `null` 通常是「解除覆寫」而不是「清空」,而解除之後會回到**真實**狀態 ——
   在一台真實狀態與期望不同的機器上,量到的就會是現況而不是你想要的。
   用一個**明確的空值**(`[]` / `''` / `false`)來代表「沒有」,並且在測試裡
   **先把真實狀態設成非空**,否則那個錯誤在測試環境裡看不出來。
6. **這個量測量的是「使用者看到的那一層」嗎?有沒有控制組?**(盲區 4 專屬)
   頁面截圖對視窗層(系統材質、webContents 底色、視窗邊框)天生是盲的。
   要嘛換一層量(OS 層擷取,座標要乘 dpr),要嘛在文件裡明寫這個邊界 ——
   但不能讓「頁面全綠」讀成「使用者看到的是對的」。而且**每一組差分都要有
   控制組**(一個「已知不該變」的組合):沒有控制組,你分不出「沒變」與
   「量測根本沒看到東西」。
